# 动态虚拟摄像头

Windows x64 OBS 的独立插件，不替换自带虚拟摄像头。通过“工具 → 动态虚拟摄像头管理”添加和管理多台设备。

## 多设备操作

- 点击“新增虚拟摄像头”，列表中新增一台设备；选中设备后，在右侧配置并单独开启。可重复添加 N 台，不使用一个固定设备供所有应用共用。
- 每台设备独立保存名称、输出类型/选择、共享内存像素格式、分数帧率、目标/最大缓冲帧数、输出相位及测试卡。可以同时开启多台；其它软件按不同设备名分别选择。
- 相位和测试卡可以在运行中独立修改，不重启接收软件，不影响其它设备。相位作用于这台设备的全部接收实例，不再按应用设置。
- 重命名需要先关闭所选设备；移除运行中的设备会先停止它。关闭/移除 A 不会注销 B。隐藏管理窗口不会停止设备，OBS 退出或切换场景集合会全部停止。
- 每台设备具有持久化的独立 GUID/CLSID，重命名不改变设备身份；每次开启还会生成新会话，避免旧客户端接入下一次输出。`devices.json` 保存目录，`device-{GUID}.json` 保存独立配置；首次升级将旧单设备配置迁移给第一台设备，不自动开启。
- 不查询、保存或显示接收端进程名称、可执行文件路径，不再提供进程列表。内部仍使用 PID/进程创建时间回收崩溃接收实例和监视 OBS 生命周期，不用于识别应用。
- 未设置设备总数的固定上限；实际数量受内存、OBS 输出/回读和生产端转换负载限制。每台有独立的所选格式队列和测试卡绘制资源，多台高清输出会增加开销。

## 输出和设备生命周期

- 输出类型包括节目、预览、指定场景、指定来源；指定来源按 OBS 画布居中等比适配。预览跟随工作室模式的预览场景，非工作室模式跟随当前场景。
- 输出分辨率沿用 OBS 视频输出，要求宽、高均为偶数且不超过 8192。默认勾选“跟随 OBS 输出帧率”，开启时读取实际 OBS 视频帧率；取消勾选后可独立输入分子、分母，支持 1–1000 FPS，分子、分母上限各为 1000000。运行时锁定格式和帧率设置，修改需先停止设备。
- 开启后才通过提权清理助手在 `HKLM\Software\Classes` 的 DirectShow 视频采集设备类别以所设设备名注册各自 CLSID，同时注册 64 位和 32 位 COM DLL；普通权限 OBS 会弹出 Windows UAC 授权，取消则不开启，关闭时由同一个助手移除。该注册不需要永久安装驱动，不覆盖自带设备，也不修改 OmniVCam。
- 动态的是设备注册和客户端进程按需加载 DLL，不是每次启停卸载 OBS 插件本身。已经缓存设备列表的软件需要重新枚举；已经加载 DLL、持有设备对象的程序不会被强制卸载。关闭后这些对象停止输出，不会转接到下一次会话。
- 设备只对同一 Windows 用户、同一登录会话的 DirectShow 客户端提供保证，兼容普通权限及管理员权限的接收程序；只支持 Media Foundation、浏览器安全策略限制、系统代理或沙箱的软件需要另外验证。没有实现系统级摄像头驱动或 Media Foundation 摄像头。
- 使用每会话唯一的共享内存和互斥对象。隐藏的提权助手在注册前验证 OBS 进程身份和共享队列，注册完成才通知界面启动成功；随后监视停止事件和 OBS 进程，正常停止、退出或崩溃后移除本会话机器级注册。系统断电时助手无法执行，下一次开启仅回收同一用户、已失效的旧注册，不覆盖活跃会话或其它用户/第三方的设备。不能保证所有软件的设备缓存即时消失。

## 接收实例和相位

面板每 500ms 更新所选设备的接收实例数、传输中实例数、交付帧数、重复画面、当前实例的旧帧丢弃数、最大待消费缓冲帧数、重新对齐次数及最近选帧复制/下游 `Receive` 耗时，不展示接收端身份。每 5 秒写入 `[dynamic-virtualcam-stats]` 到 OBS 日志，可从“帮助 → 日志文件 → 查看当前日志”查看。

日志包含设备名称/GUID、目标分数帧率、`delivered_fps`、`fresh_fps`、`expired`、`last_prepare_ms`、`last_receive_ms`、`late_ms`、最近 HRESULT、`buffer_target`、`buffer_max`、`buffered`、`rebuffers`，以及生产端成功发布帧率 `published_fps`、发布/忙槽丢帧计数、相位和像素格式。`fresh_fps` 指未重复交付的队列帧，不保证源内容发生了变化；多个接收实例的帧率按交付总和统计，不是单个播放器显示 FPS。准备/接收耗时取当前实例的最近值中的最大值，而非长期平均。

同一设备的多个接收实例共享一个相位，但各自维护消费序号，互不抢帧；不同设备的队列、时基和相位独立。关闭一个接收软件不会停止其它接收实例。

设备仍有接收实例打开时，点击关闭或移除会先确认，默认选择“否”；暂停但尚未释放的实例也算占用。正常退出 OBS（主窗口关闭、菜单退出或托盘退出）前，会汇总被占用的设备并确认；取消会保留 OBS 和输出，允许退出后仍须经过 OBS 自身可能出现的其它确认。关闭管理窗口或最小化到托盘不触发退出提醒。检测时控制锁忙则保守地提醒，刚异常退出的实例也可能短暂触发提示。强制结束进程、崩溃和系统强制关机不能保证弹窗；场景集合切换等内部停止路径不额外确认。

帧率为 `num/den` 时，接收实例的内部帧时钟为：

```
clock(n) = floor(n × 1000000000 × den / num)
```

`n` 只随实际成功交付的输出帧递增，重复画面也递增。首次缓冲未达标时尚未开始交付。该时钟不读取 QPC、不跳过实际错过的唤醒序号，也不受相位修改影响。60000/1001 的第 60000 个周期恰好是 1001 秒，不先截断整数纳秒间隔再逐帧相加。

实际等待另有独立的 QPC 调度基准 `wake_epoch` 和唤醒序号 `k`：

```
deadline(k) = wake_epoch + phase_ns + floor(k × 1000000000 × den / num)
```

`wake_epoch` 只用于计算实际等待，不是帧时间戳或选帧依据。QPC 高分辨率计时也用于耗时/迟到诊断，不参与媒体时间轴、缓冲 offset 或窗口判断。修改相位时只重新定位下一轮实际唤醒时刻，不修改 `n`、内部帧时钟、样本时间戳或直接重置 offset。已在等待的一帧继续完成，避免连续拖动取消所有输出；调节时实际交付间隔可以短暂变长或变短。相位范围仍为 `0 ≤ phase < T`，不是显示器 VSync 同步。

客户端提前获取样本缓冲，等待实际发送时刻后使用内部帧时钟选帧、复制并交付。普通视频在 OBS 侧完成格式转换；RGB 正高度样本按倒序行拷贝，YUV 不翻转。迟到时只跳过实际唤醒网格，不突发补发，也不据此推进内部帧时钟。**纳秒级是时间计算精度，不是 Windows 唤醒或接收软件物理交付精度保证。**

首次交付时从 DirectShow 参考时钟读取流起点，后续 `SetTime` 为该固定起点加 `clock(n)/100`，结束时间为 `clock(n+1)/100`；不将 QPC、相位或 OBS 时间戳混入样本时间戳。`SetMediaTime` 的帧序号连续递增。缓冲重新对齐会标记样本不连续，但不让样本时间戳或帧序号回退。

## 缓冲和选帧

每台设备启动前设置“目标缓冲帧数”和“最大缓冲帧数”，范围均为 1–30 且目标不大于最大值。新设备默认目标 2、最大 5；旧 `slots` 配置迁移为最大值。更改需要停止设备。共享内存按最大帧数分配，每槽具有独立互斥对象，高分辨率、大容量会增加内存消耗；生产端遇忙槽跳过写入，不阻塞 OBS，失败写入不占用成功帧序号。

OBS 普通画面及测试卡发布的队列帧时间戳均直接使用 `video_data::timestamp`，不再使用 QPC 发布时刻，也没有复制后按 QPC 年龄丢弃的逻辑。以下状态由各接收实例独立维护，互不抢帧：

1. 首次启动或缓冲已降至 0：等待重新攒够目标帧数。首次未攒够不交付样本；已经开始输出的实例在等待期间按内部帧率交付上一画面。
2. 未消费成功帧数超过最大值：丢弃旧帧，只保留最新的目标帧数；即使环形队列已经覆盖多轮，也按成功发布序号计算积压，不能只数当前可见槽位。
3. 达到目标后，将保留的最老帧的 OBS 时间戳记为 `source_anchor`，当前内部帧时间记为 `clock_anchor`。此时二者经 offset 对齐后的差值为 0；后续比较目标为 `source_anchor + clock(n) - clock_anchor`。实现保存两个锚点，避免跨时间域直接做有符号减法溢出。
4. 在 OBS 帧时间戳与此目标相差 `[-0.6T, +0.6T]` 的未消费帧中选择最老一帧，边界可选。落后超过窗口的帧丢弃，超前超过窗口的帧保留等待。被选帧按序号消费，同一实例不能再次当成新帧选取。
5. 输出时间戳回退或前跳超过 2 秒视为新的时间段，丢弃旧时间段，再等待目标帧数并重新对齐，避免永远等不到窗口内的帧。

例如 60 FPS、目标 2、最大 5：队列 OBS 时间戳为 1000ms、1016.666667ms 时，第一帧对齐内部 `clock(0)=0`，下一轮内部时间为 16.666666ms，比较目标约为 1016.666666ms，窗口为其前后各 10ms。调整相位只改变这一轮实际何时发送，不把相位加入上述比较目标。若积压到 6 帧，则保留最新 2 帧，以其中最老帧重新对齐当前内部时间。

没有合格新帧时重复上一画面，不将其重新消费。不同输入/输出帧率下，窗口丢弃、重复以及欠载后重新攒帧均属正常策略；帧数缓冲不能生成额外真实内容，也无法保证接收软件或显示器最终显示不丢帧。

## 相位调整测试卡

在插件面板的“相位调整测试卡”中选择：

- **关闭**：恢复原先选择的节目、预览、场景或来源画面。
- **运动**：彩条、帧号、8 个不同周期的转针、底部移动条和 32 位 Gray 编码帧条。参考 OmniVCam 的多周期转针，方便发现重复、跳跃和不均匀运动。

测试卡可运行中切换，不需要重新打开客户端；选中的输出类型、来源保留，关闭测试卡即可恢复。只替换此虚拟摄像头的输出，不修改 OBS 场景、预览、录制或自带虚拟摄像头。

测试卡由 **OBS 原始视频回调按 OBS 帧率生成**，仍经过同样的跨进程帧数缓冲队列、±0.6T 选帧与该设备的相位调度，不在客户端重新绘制运动来掩盖源帧重复。输出窗口中的帧号不变代表画面重复；但摄像头帧率低于 OBS 时，帧号正常跳跃不能直接视为异常。测试卡绘制也有处理成本；高分辨率可能增加生产端负载。

建议先使用相同的 OBS/摄像头帧率，在接收软件中查看“运动”测试卡，同时在 OBS 面板中调该设备的相位，比较运动连续性、“重复画面”和“交付迟到”。这能观察插件交付和软件接收后的表现，不代表能直接测得显示器 VSync 或扫描时刻。

`FRAME CLOCK` 是按 OBS 原始视频回调帧序号和 OBS 分数帧率计算的时间，不是 QPC、接收端内部时钟、显示时刻或相位；`OBS PTS` 是实际随画面发布到共享队列的 OBS 输出时间戳。

旧设置中的校准测试卡自动改为运动测试卡，避免升级后意外显示真实视频内容。

## 像素格式

在 OBS 面板启动前选择 NV12、YUY2、RGB24、RGB32、ARGB32 中的一种格式，默认 NV12。该设备的共享内存、DirectShow 能力列表和 FilterData 均只使用这一种格式；不再让每个接收端临时转换为不同格式。如不同软件需要不同格式，可新增不同设备。普通视频由 OBS 端转换服务输出目标格式；运动测试卡先绘制 BGRA，再在 OBS 进程转换一次后发布，多个接收端共用转换结果。用户提到的 `RGBA24` 按“四个 8 位通道”的 32 位格式处理，标准名称不是 RGBA24。DirectShow RGB24 内存为 BGR，RGB32 为 BGRX，ARGB32 为 BGRA，不能与字节序 RGBA 混为一谈。ARGB32 测试卡的 alpha 为不透明，普通视频保留 OBS 转换输出的 alpha。

DirectShow 能力枚举与格式协商全部使用正的 `biHeight`，拒绝负高度。RGB24/RGB32/ARGB32 为底部起始（内存第一行是画面最下面一行），RGB24 保留 DWORD 行对齐并清零填充字节；YUY2/NV12 仍为顶部起始，按 BT.709 limited range 转换，不翻转 YUV。共享内存统一保存顶部起始图像，RGB 接收端倒序拷贝到样本，重复画面也使用相同方向；缓存通过交换缓冲保存，不为 RGB 新帧额外复制整张图像。当前不提供任意分辨率、任意帧率协商：先在 OBS 面板设置，重启设备后由客户端刷新能力列表。更换输出类型、像素格式、帧率或容量需要先停止；相位可以实时修改。

插件自带的 BGRA 转换使用 SSE2 批量计算 RGB32/ARGB32、YUY2 和 NV12；RGB24 检测 SSSE3 后使用字节重排压缩，不支持时退回标量，不要求 AVX2。YUV 系数、色度取平均的舍入顺序与标量实现一致，避免 SIMD 引入色差。尾部不足一个向量时单独处理，允许未对齐指针，不越界读取或写入。该路径用于测试卡和初始化图像；普通视频仍使用 OBS/FFmpeg 的转换服务，不修改 OBS 全局转换链路。

## 接口与高清调试构建

输出 pin 可查询 `IID_IKsPropertySet`。`QuerySupported(AMPROPSETID_Pin, AMPROPERTY_PIN_CATEGORY)` 返回仅 GET，`Get` 返回 `PIN_CATEGORY_CAPTURE`，支持查询所需大小；该属性只读，未知属性集/ID 返回对应不支持错误。接口遵循同一 COM `IUnknown` 身份和引用计数。

### 与 OmniVCam 的枚举兼容性对比

| 项目 | 当前插件与 OmniVCam 的区别 |
| --- | --- |
| 主要视频接口 | 两者均提供 `IBaseFilter`、`IPin`、`IAMStreamConfig`、`IKsPropertySet`；当前插件还提供 `IAMFilterMiscFlags`。 |
| `IMemInputPin` | OmniVCam 的视频输出 pin 也暴露此接口；当前插件不为输出 pin 提供输入语义，不将其作为设备枚举的必要条件。 |
| `IAMBufferNegotiation` | OmniVCam 的音频 pin 提供，视频 pin 未提供；当前插件仅提供视频。 |
| 属性页和相机控制 | 两者的视频实现均未提供 `ISpecifyPropertyPages`、`IAMVideoProcAmp`、`IAMCameraControl`，不是当前已确认的差异。 |
| 能力列表 | 当前插件只列出启动前所选的单一像素格式，尺寸和帧率取自 OBS 面板；OmniVCam 还提供 IYUV 等能力。 |
| 注册 | OmniVCam 使用 `IFilterMapper2::RegisterFilter` 生成能力元数据；当前插件使用提权助手进行临时机器级注册，并生成同等结构的 `FilterData`。 |

旧版只写设备名称和 CLSID，没有 `FilterData`：普通设备枚举可找到，但按视频格式筛选的 `IFilterMapper2::EnumMatchingFilters` 无法找到。集成测试已复现此差异。现由 Windows Filter Mapper 序列化所选单一媒体类型、输出 pin 和 `PIN_CATEGORY_CAPTURE`，将二进制能力描述写入 32/64 位设备注册，并移除原先伪造的 `DevicePath`。

能力元数据修复筛选枚举缺口；后续实测又定位到管理员接收程序无法激活用户级 COM 类的问题，现通过临时机器级注册处理。升级后先开启设备并允许 UAC，再完全退出并重开直播伴侣以刷新缓存。普通/管理员权限激活和送帧测试不能替代所有版本直播伴侣的 UI 实测。

历史实现把 BGRA 放进共享内存，再由每个接收线程逐帧转换：1080p Debug 下优化后的 NV12 转换仍需约 4–5ms，提前选帧会漏掉转换期间刚到达的帧。现在移除交付路径的逐帧颜色转换，并将选帧推迟到逻辑目标时刻；测试卡使用的生产端 `pixels.cpp` 在 Debug 中仍启用优化。面板统计之前误取了输出类型数据而不是输出实例，导致统计不刷新、日志不打印，现改为获取实际实例。

测试增加了每秒只生产 60 帧、带 ±2ms 发布抖动的 1080×1920 NV12 场景，覆盖 8ms、15ms 相位；生产端等待使用高分辨率定时器，避免 `Sleep(1)` 的唤醒粒度掩盖设定的抖动。测试报告交付率和新帧率，不将 `Receive` 成功等同于播放器最终显示。帧数缓冲和 ±0.6T 窗口仍不能弥补生产端长时间无帧或系统/下游阻塞；当前结果不能代替 PotPlayer、直播伴侣实测。

替换测试版本时，先关闭 OBS 及所有打开此虚拟摄像头的软件，再完整替换 OBS 模块、32/64 位过滤器和清理助手。当前共享内存协议为 1，包含缓冲目标、OBS 时间戳及时间段标记；插件尚未发布，不保留此前测试版本的协议兼容逻辑，各组件须使用同一构建版本。注册只在开启期间存在，不需要手工 `regsvr32`。

## 管理员权限应用的设备发现诊断

旧版设备的 COM 类及 DirectShow 类别项只注册在 `HKCU\Software\Classes`，而不是 `HKLM`。不能只凭普通权限的枚举测试通过，就认为管理员权限的接收程序也能打开设备。

修复前在开发机上已复现：普通权限进程可以枚举本设备，且 `IMoniker::BindToObject` 返回 `S_OK`；同一个探针提升为管理员权限后，仍能枚举名称，但激活返回 `0x80040154`（`REGDB_E_CLASSNOTREG`）。因此，枚举后尝试激活、并过滤失败设备的应用可能不显示本设备。直播伴侣的实际日志显示其媒体服务使用管理员模式，设备列表中没有本设备；这与该权限差异吻合，不应继续仅通过增加媒体格式或 COM 接口尝试解决。

可使用只读探针对正在运行的设备做检查，不会注册、注销设备或启动送帧线程：

```
dvc-device-check.exe --inspect {设备CLSID} [报告文件路径]
```

探针输出自身是否提升、位数、设备列表及目标设备的激活 HRESULT。分别在普通权限和管理员权限下运行；返回码 `0` 表示目标设备枚举和激活成功，`1` 表示枚举失败或未找到，`2` 表示参数/报告文件错误，`3` 表示枚举到但无法激活。

正式启动现使用 `dvc-watchdog.exe --register-machine` 请求提权，在两个注册表视图中同时写入机器级 COM 类、设备类别与能力元数据，并承担整个会话的注销。旧的用户级注册会在升级后下次启动时按会话标记清理；底层用户级 API 仅保留给兼容性测试。无需让整个 OBS 以管理员身份运行，也不安装常驻服务或计划任务。不得手动只复制类别项或永久注册临时会话。

## 构建和测试

构建 `dynamic-virtualcam` 会同时构建、打包 64/32 位 `dvc-filter` 和清理助手；跨架构 CMake 子构建不依赖 Qt 或 OBS DLL。摄像头 DLL 和助手静态链接 MSVC CRT，不要求其它应用加载 OBS/FFmpeg。

```
cmake --build build_x64 --config Debug --target dynamic-virtualcam dvc-tests dvc-output-tests
build_x64\plugins\dynamic-virtualcam\Debug\dvc-tests.exe
```

`dvc-tests` 不注册真实摄像头，覆盖分数时钟、窗口边界、一次性消费、多消费者队列、1–30 槽覆盖、客户端记录、RGB 行对齐和 YUV 转换，并直接连接 DirectShow 输出 pin 与测试接收 pin，验证五种格式在 2×2、1920×1080 下的分配、协商、实际交付、运行中相位修改、IKsPropertySet 契约和清理；测试卡与不同设备队列/相位隔离也有覆盖。输出实际送帧率供诊断，不断言所有机器都能达到相同性能。目标软件显示兼容性、更高分辨率、N 台总负载和长期相位抖动仍需实测，不以单元测试代替。

`dvc-buffer-tests` 可分别构建 x64/x86；`dvc-tests --buffer-only` 可运行同一组回归。覆盖首次攒帧、清空后重新攒帧、超过最大值及覆盖多轮后保留目标数量、±0.6T 两端边界和最老优先、消费不重复、OBS 时间戳为 0/巨大值/回退/大幅前跳、多接收实例独立 offset、忙槽失败不制造序号空洞。60000/1001 连续测试 60001 次选帧，过程中修改相位与实际等待基准，验证内部选帧不受影响且无分数累计误差。相位 DirectShow 回归同时验证样本时间戳严格按帧序号连续递增。

`dvc-tests --phase-updates-only` 可单独运行实时相位回归：在 60/1 和 60000/1001 帧率下每约 1ms 连续更新相位，覆盖正反向拖动、跨周期及 0/最大值切换；启用真实 DirectShow 系统参考时钟，检查调整过程中持续送出新画面、流时间戳和媒体帧序号单调、没有长时间交付中断。旧调度在该测试中会因反复取消输出或重复媒体帧序号而失败。

`dvc-ui-tests` 是独立的 Qt 确认框回归，不加载 OBS、不注册摄像头：覆盖退出取消/允许、重复关闭及重入、OBS 后续取消退出后再次提醒、默认和关闭弹窗保留输出，以及关闭管理窗口/隐藏不触发主窗口退出检查。运行前将 Qt 的 `bin` 加入 `PATH`，设置 `QT_QPA_PLATFORM=minimal` 和 `QT_PLUGIN_PATH` 到对应 Qt `plugins` 目录即可无可见窗口运行。该测试不代替真实接收软件保持连接时的 OBS 端到端验证。

`dvc-pixel-tests` 可分别构建 x64/x86 版本：逐字节比较 SIMD 与标量，覆盖随机/极值颜色、RGB 行翻转、奇数 RGB 宽度、DWORD 填充、未对齐地址、向量尾部和 1080p/4K，并用不可访问保护页检查图像末尾越界。加 `--benchmark` 输出同一构建下的转换耗时对比；结果仅代表这台机器的 CPU 转换，不包含测试卡绘制、OBS/FFmpeg 转换、共享内存和接收/显示耗时。

`dvc-output-tests` 额外启动独立 libobs 实例，初始化一个 16×16 D3D11 视频上下文，不创建预览窗口、不注册设备。它向独立 1280×720 原始视频输出送入已知图像，验证五种格式的 OBS 实际预转换、共享内存内容、跟随 60000/1001 / 手动 24/1 帧率配置和运动测试卡，共 15 个组合。运行时将 OBS 运行目录的 `bin/64bit` 设为工作目录并加入 DLL 搜索路径，再用绝对路径启动测试 EXE；需要该目录的 OBS/D3D11 DLL 和对应 `data/libobs` 资源。这是转换与配置测试，不是播放器显示帧率测试。

另有显式运行的 `dvc-device-check` 集成测试，**会临时修改当前用户的设备注册**，使用随机独立测试 GUID，不修改用户已配置的设备；仍建议在其它采集软件关闭时运行。分别构建 x64、x86 的该目标后，运行 x64 版本：

```
dvc-device-check.exe --registration <绝对路径/dvc-filter64.dll> <绝对路径/dvc-filter32.dll> <绝对路径/dvc-watchdog.exe> <绝对路径/32位dvc-device-check.exe>
```

该测试通过真正的 DirectShow 普通设备枚举、所选格式的筛选枚举（包括 capture pin 类别），并确认其它四种格式不误报和 moniker 激活 DLL，并确认不误报未支持的 MJPG。让 64/32 位独立进程同时接收画面，验证多个独立 CLSID 和队列、不同设备相位、关闭一个不影响其它设备，检查正常移除，再终止专用发布子进程验证助手的崩溃清理。不启动 OBS 或使用物理摄像头，不删除其它设备。测试失败中止时由助手清理本测试注册。该测试已在开发机通过，但不代表所有第三方软件兼容。

`dvc-device-check --machine-registration <dll64> <dll32> <watchdog> <probe32-exe>` 是额外的机器级集成测试，需要允许数次 UAC。它由普通权限进程生产测试帧，验证普通/管理员权限的 32/64 位客户端均能激活和接收；另外覆盖双设备隔离、停止及专用生产子进程崩溃后的机器级清理、失效会话回收及旧会话不能误删新会话。仅使用随机测试 CLSID，不修改用户正在使用的摄像头。
